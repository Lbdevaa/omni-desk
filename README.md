# omni-desk

**Рабочее место оператора поддержки: одна лента переписок из всех каналов, один экран
для ответа и гарантия, что двое не ответят одному клиенту, а отправленное сообщение
не задвоится и не потеряется.**

---

## Задача

Клиенты пишут в Telegram, WhatsApp, почту и чат на сайте. Шлюз приводит это к единому
виду — но дальше с потоком должен работать живой человек, и здесь начинаются проблемы,
которых нет в спецификации API.

Диалог видят все операторы сразу, и двое берут его одновременно — клиент получает два
разных ответа от двух людей и решает, что с ним разговаривает бардак. Оператор отправляет
ответ, интерфейс подвисает на несколько секунд, потому что запрос ушёл во внешний API
и ждёт его. Сообщение отправлено дважды, потому что кнопку нажали повторно. Лента
подгружает следующую страницу, а пока она грузилась, сверху пришли новые сообщения —
и часть старых исчезла из списка навсегда.

Всё это — не проблемы вёрстки. Это конкурентный доступ, ненадёжная сеть и данные,
которые меняются во время чтения.

omni-desk — реализация такой панели, спроектированная вокруг этих трёх проблем.

## Что делает

- **Показывает** ленту диалогов с курсорной пагинацией: она остаётся корректной,
  пока сверху приходят новые сообщения
- **Закрепляет** диалог за оператором так, что второй получает отказ, а не молча
  перезаписывает первого
- **Отправляет** ответ через очередь: интерфейс не ждёт внешний API, а повторные
  попытки и отказы обрабатываются воркером
- **Не двоит** сообщения: повторный запрос и приход собственного сообщения по подписке
  распознаются по ключу идемпотентности
- **Обновляется в реальном времени**: новое сообщение появляется в открытом диалоге
  без перезагрузки, подписка на чужой диалог отклоняется
- **Разграничивает доступ** политиками: оператор видит свои и свободные диалоги,
  а не всё подряд

## Проектные решения и их причины

| Решение | Что было бы иначе |
|---|---|
| Захват диалога — транзакция с блокировкой строки, конфликт отдаёт `409` | проверка «свободен ли диалог» перед сохранением пропускает второй запрос в промежуток между чтением и записью: оба оператора получают успех и отвечают одному клиенту |
| Курсорная пагинация вместо `LIMIT/OFFSET` | лента пополняется сверху прямо во время скролла — смещение съезжает, и записи пропадают из выдачи или приходят дважды |
| Ответ ставится в очередь, а не отправляется в HTTP-запросе | оператор ждёт ответа внешнего API; при таймауте провайдера интерфейс подвисает, а сообщение теряется вместе с упавшим запросом |
| Ключ идемпотентности генерирует клиент, на нём уникальный индекс | повторное нажатие, ретрай при сетевом сбое и приход собственного сообщения по подписке — три независимых источника дублей в переписке |
| Сессия в `httpOnly` cookie (Sanctum SPA), а не токен в `localStorage` | токен из `localStorage` читается любым XSS, в том числе занесённым через зависимость |
| Подписка на канал диалога авторизуется на сервере | публичный канал означает, что чужая переписка читается по угаданному идентификатору |
| Правила доступа в политиках, а не в контроллерах | одно и то же правило дублируется по эндпоинтам и со временем расходится — на части из них его просто забывают |
| Индексы под конкретные выборки, а не «на каждое поле» | лишний индекс замедляет запись и занимает место, не ускоряя ни один реальный запрос |
| Виртуальный скролл на переписке | диалог в тысячу сообщений держит тысячу узлов в DOM: прокрутка начинает тормозить на самых активных клиентах — то есть на самых важных |

## Модель данных

| Таблица | Назначение |
|---|---|
| `users` | операторы |
| `contacts` | клиент в конкретном канале: канал, внешний идентификатор, имя |
| `dialogs` | переписка с контактом: закреплённый оператор, статус, время последнего сообщения, непрочитанные |
| `messages` | сообщение: диалог, направление, текст, внешний идентификатор, ключ идемпотентности, статус отправки |

Ключевые индексы: составной `messages (dialog_id, id)` — выборка переписки курсором;
составной `dialogs (operator_id, last_message_at)` — лента оператора;
уникальные `messages (channel, external_id)` и `messages (idempotency_key)` —
идемпотентность приёма и отправки.

## Запуск

Требуется PHP с включёнными `pdo_pgsql` и `pgsql`, Node.js, Docker.

```bash
docker compose up -d                   # PostgreSQL и Redis

cd api
composer install
cp .env.example .env && php artisan key:generate
php artisan migrate --seed             # схема и демонстрационные данные
php artisan serve
php artisan queue:work                 # отдельным процессом

cd ../web
npm ci
ng serve                               # localhost:4200
```

PostgreSQL опубликован на порту `5433`, чтобы проект работал одновременно
с [omni-relay](https://github.com/Lbdevaa/omni-relay). Оба порта слушают только `127.0.0.1`.

- SSR включён только на одну публичную страницу; приложение за авторизацией остаётся клиентским — индексировать там нечего, а Node-процесс рядом с PHP это ещё один сервис в эксплуатации

## Связь с omni-relay

[omni-relay](https://github.com/Lbdevaa/omni-relay) — шлюз входящих сообщений на NestJS:
принимает вебхуки мессенджеров, нормализует их и складывает в PostgreSQL, гарантируя,
что повторная доставка не создаст дубль.

omni-desk — рабочее место поверх этого потока. Панель читает переписку, а ответ оператора
публикует в очередь `messages.outgoing`, откуда его забирает отправитель шлюза.

Разделение зон ответственности осознанное: шлюз ничего не знает про операторов и интерфейс,
панель — про подписи вебхуков и лимиты провайдеров. Каждый из двух сервисов запускается
и работает самостоятельно.
